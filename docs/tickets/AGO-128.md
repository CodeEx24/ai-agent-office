# AGO-128 - US-021 Build the skill library with versions

## Overview
Epic EP-03 (Skills and capabilities), wave 2 (Agent Runtime + Guardrails), workstream WS-C (Web App and UX), risk tier **high** (data model, authorization, untrusted-text rendering, human-in-the-loop surface). Jira: https://stratyge.atlassian.net/browse/AGO-128. Blocked by AGO-74 (core schema) and AGO-107 (RLS on every table), both done.

"As an owner, I want to create, version and assign Markdown skills so that agents have know-how I control."

Acceptance criteria (verbatim):
- Given a skill edit, when saved, then a new version is stored and the old one remains
- A skill can be assigned to and removed from an agent
- Skill text shows a preview
- Tests pass, no regressions, PR reviewed and merged, docs updated (see Definition of Done)

A skill is **know-how, not permission**: it never grants a capability (AGO-125). Skill text is untrusted data (CLAUDE.md), so it is rendered without raw HTML and never treated as instructions to the platform.

## Implementation details
**Database** (`supabase/migrations/20261106150001_ago_128_skill_versions.sql`, rollback in `supabase/rollbacks/`):
- `skills` (AGO-74, seeded by AGO-122) is extended, not duplicated. It stays the *current* row: `body` and `version` mirror the newest version, so the seed, the AGO-107 tests and the future context builder (AGO-145) keep reading one row. A CHECK caps `body` at 20,000 characters.
- `skill_versions` is the immutable history: `(workspace_id, skill_id, version, body, created_by, created_at)`, unique per `(workspace_id, skill_id, version)`, composite FK to `skills` and to `members` (`created_by`, the owner who saved it). Existing skills are backfilled as their current version.
- Versioning is done by triggers, so no code path can edit a skill without leaving a version behind: a `BEFORE UPDATE` trigger (`private.bump_skill_version`) sets `version = old.version + 1` only when `body` changes; an `AFTER INSERT OR UPDATE` trigger (`private.append_skill_version`, SECURITY DEFINER, pinned `search_path`, execute revoked) appends the row. `version` is in no grant.
- Immutability for **every** role including `service_role`: `private.skill_versions_block_change` raises `42501` on UPDATE, and on DELETE unless the parent skill or workspace is already gone (the FK cascade). API roles have SELECT only.
- RLS (AGO-107 pattern, per command, `private.is_member`): `skill_versions_select_viewer`; `skills_insert_owner` / `skills_update_owner`; `agent_skills_insert_owner` / `agent_skills_delete_owner`. The old member-level write policies and the `delete` grant on `skills` are removed.

**Shared** (`packages/shared/src/skills/skill-schemas.ts`): `SKILL_BODY_MAX_LENGTH` (20,000, mirrors the DB), name/description/body schemas (body line endings normalised CRLF to LF before the size check, because browsers submit CRLF), `createSkillSchema`, `saveSkillSchema` (with `expectedVersion`), `assignSkillSchema`, row schemas.

**Web** (`apps/web/src/features/skills/`, feature-first): `skill-library.ts` (server-only data layer: `listSkills`, `getSkillDetail`, `createSkill`, `saveSkill`, `assignSkill`, `unassignSkill`; every call goes through `requireWorkspaceRole`, rows are parsed with Zod), `actions.ts` (four server actions, each `parseInput`), `MarkdownPreview.tsx`, `SkillEditor.tsx` (live preview), `CreateSkillForm.tsx`, `AssignSkillPanel.tsx`, `VersionHistory.tsx`. Routes stay thin: `/app/skills` and `/app/skills/[skillId]` (the id is validated with `parseInput`; a bad or foreign id is a 404). A "Skills" link was added to `/app`.

**Markdown preview.** `react-markdown` (new dependency, see decisions) with `skipHtml`, no `rehype-raw`, `img/script/iframe/style/object/embed/form/input` disallowed, and a link allow-list (`http(s)`, `mailto`, `#anchor`, site-relative; `javascript:`, `data:`, `vbscript:`, `//host` and whitespace-obfuscated schemes are blanked so the link falls back to plain text). External links get `rel="noopener noreferrer"` and `target="_blank"`. No `dangerouslySetInnerHTML`, so it works under the AGO-66 strict script CSP.

**Shared helper fix.** `formDataToRecord` now drops Next.js `$ACTION_*` form fields, so strict Zod schemas work on server-action forms (found by the live test; unit-tested).

### Decisions taken (no human at the keyboard; recommended option chosen each time)
| Decision | Chosen | Why |
|---|---|---|
| Extend or replace `skills` | Extend: keep `skills` as the current row, add `skill_versions` | Reuse-first; AGO-122 seed, AGO-107 tests and future readers keep working. "Current = latest" needs no pointer column that could drift. |
| How versions are created | Database triggers (bump + append) | Atomic with the edit and impossible to bypass from any code path, `service_role` and the seed included. No RPC to audit. |
| Which edits make a version | A change of `body` only | The version is the skill's text. Editing the description or saving identical text adds nothing. |
| Immutability | Privileges (SELECT only) plus a trigger that raises for every role; DELETE allowed only for the FK cascade | Meets "no update/delete grants" and holds even for `service_role`. Blocking all deletes would make removing a workspace or a skill impossible. |
| Who writes | Owners only (create, edit, assign, remove); members and viewers read | CLAUDE.md human-in-the-loop; agents are never members. This tightens the AGO-107 member-level policies, and the tests that encoded "member can write" are updated. |
| Deleting a skill | No API delete (grant removed) | Versions are history and assignments reference the skill; retiring/archiving is a follow-up. |
| Assignment: pin a version or follow latest | Follow latest (no pin column) | Pinning needs an UPDATE grant and policy on `agent_skills` and no AC asks for it. The context builder (AGO-145) is the consumer that would need it. |
| Stale editors | `expectedVersion` sent with the form; the update is `where version = expected`; zero rows means "someone saved first" | Two owners cannot silently overwrite each other; costs one hidden field. |
| Size limit | 20,000 characters, in the DB (CHECK) and Zod, one constant | Bounds the untrusted text; large enough for a long skill. |
| Markdown renderer | Add `react-markdown` (no raw HTML plugin) | Safe by default, no `dangerouslySetInnerHTML`. Not in the locked-stack list, and not a replacement of anything in it; the alternative is a hand-written sanitizer, which is riskier. |
| Where to assign | On the skill page (pick an agent, remove button) | There is no agents page yet (AGO-141 is the wizard). Satisfies AC2 without building agent CRUD. |
| Rate limiting | Reuse the proxy rule for `POST /app/*` (60 per minute per user) | Server actions are POSTs under `/app`, so they are already covered (AGO-66). |

## API changes
No new HTTP routes. New pages `/app/skills` and `/app/skills/[skillId]` (session cookie; viewer or higher reads, owner writes). Four server actions (`createSkillAction`, `saveSkillAction`, `assignSkillAction`, `unassignSkillAction`), each validated with `parseInput` and gated by `requireWorkspaceRole(..., "owner")`. Data API: `authenticated` gets SELECT on `skill_versions`, INSERT/UPDATE (owner) on `skills` columns `(workspace_id, name, description, body)` / `(name, description, body)`, INSERT/DELETE (owner) on `agent_skills`; `anon` nothing.

## Database changes
- `20261106150001_ago_128_skill_versions.sql`: CHECK on `skills.body`, table `skill_versions` (RLS, select policy), backfill, 3 trigger functions (2 SECURITY DEFINER with pinned `search_path`, execute revoked), triggers, owner-only policies on `skills` and `agent_skills`, `delete` grant on `skills` revoked.
- Rollback: `supabase/rollbacks/20261106150001_ago_128_skill_versions.down.sql` (restores the AGO-107 member-level policies and the delete grant). `scripts/ago-128-rollback.test.mjs` applies it, checks, re-applies and compares `pg_dump -s` (empty diff). The history is lost on rollback (local data); the current text stays in `skills`.
- `packages/shared/src/db/database.types.ts` regenerated with `pnpm db:types`.
- Existing pgTAP and live-spec files that encoded "a member can write skills" or hard-coded the table count were updated: `core_schema`, `core_schema_qa`, `rls_every_table`, `rls_every_table_qa` (16 tables, owner-only skill writes, `skill_versions` in the role matrix), and `e2e/support/rls-world.ts` plus `rls-every-table-live.spec.ts`. `docs/database.md` has the new matrix rows and a Skill library section.

## Known limitations
- No archive/delete of a skill from the UI or API (versions are history); to be added with a retire flag.
- Assignments always follow the latest version; pinning a version is a follow-up.
- No "restore this version" button: copy an old version's text into the editor and save (that stores a new version).
- `created_by` is shown nowhere in the UI yet (only stored).
- The live specs run against the shared local database and leave their users, workspaces, runs and events behind; `supabase db reset` cleans it (the seed idempotency tests assert there are no runs or events).
- The AGO-154 protection of skills from agent edits is not part of this ticket; here agents simply have no write path (no membership, no grant).
