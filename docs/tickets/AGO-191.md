## Overview
One versioned JSON format for a team of agents, so it can move between computers. This ticket
defines only the format: a Zod schema, a version migration function and a generated JSON Schema
file, all in `packages/shared`. Export (AGO-192) and import (AGO-193) build on it later and share
this one code path (CLAUDE.md §4, agent packs).

## Intent
Pack = `packVersion`, `metadata` (name, exportedAt, exporter app version), `agents[]`, `skills[]`,
optional `notes[]`. Agent = name, role, model, thinking effort, prompt, skill names, capabilities
(name and scope), daily budget, autonomy mode, department name. Skill = name, version, Markdown body.

Assumptions (source in brackets):
1. `packVersion` is an integer, v1 = `1` (guess; matches `skills.version`).
2. Strict objects everywhere, so unknown fields (ids, run history, credentials) are rejected with the field path (ticket AC, existing pattern).
3. Capability `name` is the catalog key (`vault.read`); `scope` uses the existing scope enum (code: `capability-schemas.ts`). No tier and no mode in the pack: the importer reads tiers from the catalog and lands every agent in Strict (CLAUDE.md).
4. `autonomyMode` accepts `strict | standard` (code: `POLICY_AGENT_MODES`); informational, import forces Strict (CLAUDE.md).
5. Budget is `dailyBudgetCents`, an integer (code: DB `daily_budget_cents`). The schema does not apply the workspace cap; the importer ignores and reports budgets above it (CLAUDE.md).
6. Thinking effort is `low | medium | high` (guess; no existing enum in the repo).
7. Department is an optional name string, never an id. Agents reference skills by name; every referenced name must exist in `skills[]` and names are unique (guess, enforced by a refinement with a field path).
8. Text limits reuse the existing agent/skill limits (code).
9. Notes are `{ title, body }` Markdown. All pack text is untrusted data.
10. Generator: `pnpm --filter @ago/shared pack:schema` builds then writes `packages/shared/schemas/agent-pack.v1.schema.json` via Zod 4 `z.toJSONSchema` (no new dependency). A test fails when the committed file is stale. No workflow edit: "generated in CI" is met by that check running in the existing `pnpm test` CI step.

## Acceptance criteria
- [ ] Given a valid pack, when parsed with the Zod schema, then it passes; unknown fields and wrong types are rejected with the field path
- [ ] Pack never contains secrets, database IDs, run history or approval history; broker secrets appear only as named references
- [ ] packVersion is required and a migration function exists for older versions
- [ ] JSON Schema file is generated in CI and committed so editors can validate packs
- [ ] Tests pass, no regressions, PR reviewed and merged, docs updated (see Definition of Done)

## Design
- `packages/shared/src/packs/agent-pack-schemas.ts`: Zod schemas and types (`agentPackSchema`, `AgentPack`, `PACK_VERSION`).
- `packages/shared/src/packs/agent-pack-migrate.ts`: `migrateAgentPack(input)`: reads `packVersion` first (required integer), runs a chain of per-version steps up to current, rejects unknown or newer versions with a clear error, then returns unvalidated data for the schema. The chain is empty at v1; the mechanism is tested with injected steps.
- Secrets guard: a refinement scans every string in the pack with the existing redaction detectors and rejects secret-looking text with its path. Only `secret:<name>` references (`secretRefSchema`) are allowed where a credential is mentioned.
- `packages/shared/src/packs/generate-json-schema.ts` plus a package script `pack:schema`; committed output `packages/shared/schemas/agent-pack.v1.schema.json`; staleness test.
- Barrel: one additive export line in `packages/shared/src/index.ts`.
- Docs: `docs/features/agent-packs.md`.
- No migration, no API, no UI.
