# AGO-151 - Add the pg-boss job queue

## Overview
Jira: [AGO-151](https://stratyge.atlassian.net/browse/AGO-151) (US-028), epic EP-02, wave 2 (Agent Runtime + Guardrails).

Adds enqueue, claim, retry and idempotent processing of runs to the worker with pg-boss (locked stack,
CLAUDE.md §2). Blocked-by AGO-143 (worker skeleton) and AGO-74 (core schema) are both Done.

Acceptance criteria and where they are proven:

| AC | Proof |
|---|---|
| Given a duplicate enqueue, when processed, then only one run executes | `job-queue.integration.test.ts` "AC1" (8 concurrent enqueues of one run -> 1 job, 1 execution; 4 different idempotency keys for one run -> 1 execution, via the database claim); `run-processor.test.ts` "skips a duplicate job" |
| Failed jobs retry with backoff up to a limit | `job-queue.integration.test.ts` "AC2" (attempts 0,1,2 for `retryLimit: 2`, gaps >= 0.9 s, then dead-letter); `run-processor.test.ts` retry / final-attempt cases |
| Queue depth is exposed to health | `health.test.ts` (depth passthrough), `job-queue.integration.test.ts` "AC3", `scripts/ago-143-acceptance.test.mjs` AC1 (live `/health` shows `queue.depth`) |
| Tests pass, no regressions, docs updated | `pnpm lint && pnpm typecheck && pnpm test`, `supabase test db`, this file |

## Implementation details
New module `apps/worker/src/queue/`:

- `run-job.ts` - queue names (`agent-run`, dead letter `agent-run-dead`), the retry policy, the job
  payload (`{workspace_id, run_id}`, strict Zod: ids only, never prompts or secrets) and the idempotency key.
- `run-store.ts` - `RunStore` port + Postgres implementation. Every statement is scoped by `workspace_id`.
  `claimRun` is a conditional `update ... where status = 'queued' returning` - the database-side guard.
- `run-processor.ts` - the job handler: validate payload -> claim -> emit `run.started` -> `RunExecutor`
  -> emit `run.completed`. A failed attempt before the limit hands the run back (`running` -> `queued`) and
  rethrows so pg-boss retries with backoff. The last attempt marks the run `failed`, emits `run.failed`
  (scrubbed, 300-char message), reports to Sentry with `run_id`/`agent_id`/`workspace_id`, and rethrows so
  pg-boss dead-letters the job.
- `job-queue.ts` - `createJobQueue`: owns the `PgBoss` instance, queues, consumer, `enqueueRun`, `health()`
  and graceful `stop()`.

Wiring (AGO-143 / 164 / 104):

- `main.ts` creates the queue after the logger and error tracker, uses `queue.health()` for `/health`
  (replacing `queueNotConfigured` in the worker), starts it in the background and drains it first in `stop()`.
- `health.ts` gains `QueueReport` (`status` + optional `depth`). `queue: down` is `degraded` (HTTP 200), a
  database outage is still the only 503. `queueNotConfigured` stays exported for tests and tools.
- `config.ts` gains `QUEUE_CONCURRENCY` (default 2) and `QUEUE_SHUTDOWN_TIMEOUT_MS` (default 25000).
- Events come from `createRunEventEmitter` (`run.created` on a *new* job only, `run.started`, `run.completed`,
  `run.failed`). The logger uses `withContext` so every line carries the run/agent/workspace ids.

How the guarantees hold:

- **Idempotent enqueue (layer 1):** queue policy `exclusive` + `singletonKey` = `<workspace>:run:<run_id>`
  (or `<workspace>:key:<caller key>`). pg-boss allows one queued-or-active job per key, so duplicates and
  concurrent enqueues return `null` (no new job).
- **Idempotent processing (layer 2):** even if two jobs exist for one run (different caller keys, a redrive, a
  manual insert), only the one whose `update ... where status = 'queued'` succeeds executes; the other
  completes as `skipped_duplicate`.
- **Crash recovery:** pg-boss retries a job whose worker died after `expireInSeconds`. A retry (attempt > 0)
  may take back a `running` run whose `updated_at` is older than that expiry; a first attempt never does.
- **Retries:** `retryLimit 4`, `retryDelay 5 s`, `retryBackoff` on, `retryDelayMax 300 s` (pg-boss adds jitter).
  The stored queue settings are re-applied with `updateQueue` on every start so the code is the source of truth.
- **Dead letter:** exhausted jobs are copied to `agent-run-dead` and counted in `/health` as `depth.dead_letter`.
- **Shutdown drain:** `stop()` calls `boss.stop({graceful: true, timeout})`; running jobs finish, then the
  health server, database pool and Sentry close. Past the timeout the job `signal` is aborted.

### Decisions taken (no human at the keyboard; recommended option picked)

| # | Decision | Reason |
|---|---|---|
| D1 | pg-boss installs and upgrades its own tables at start (`boss.start()`); the migration only creates and locks the `pgboss` schema | pg-boss versions its own DDL; a hand-copied copy would drift on every upgrade. The migration still gives a reviewable, reversible place for the access rules. |
| D2 | Dedupe with queue policy `exclusive` + `singletonKey`, plus a conditional-update claim on `public.runs` | AC1 says "even concurrent enqueues cannot double-execute"; the DB guard holds even when pg-boss's dedupe is bypassed. No schema change to `runs` is needed (`status` is free text). |
| D3 | Idempotency key = run id by default, or a validated caller key, always prefixed by `workspace_id` | Tenants can never collide; the run id is the natural key. |
| D4 | `run.created` is emitted only when a new job was actually queued; the job payload is ids only | Keeps the append-only log free of duplicate `run.created` rows; no prompts or secrets in the queue. |
| D5 | Queue depth is read with SQL on `pgboss.job`, not `getQueueStats` | `getQueueStats` serves a cache refreshed by a background pass (up to 1 h old) - proven stale in testing; health needs a live number. |
| D6 | The queue starts in the background and retries every 5 s; `/health` says `queue: down` (200, `degraded`) until it is up | A worker booting before the database must not crash-loop; existing "db unreachable -> 503" behaviour is unchanged. |
| D7 | No agent loop yet: `RunExecutor` is a port (`startWorker({ runExecutor })`). Without one the queue accepts jobs and nothing consumes them | The loop is AGO-167 (not started). A fake "completes instantly" executor would mark runs done that never ran. |
| D8 | `pnpm test:e2e` not run | No UI or web route changed; the worker has no browser surface. |

## API changes
No HTTP route added. `GET /health` and `/healthz` change shape compatibly:

```json
{ "status": "ok", "db": { "status": "ok" },
  "queue": { "status": "ok", "depth": { "queued": 0, "active": 0, "failed": 0, "dead_letter": 0 } },
  "uptime_s": 12 }
```

`queue.status` is `ok` or `down` in the worker (was `not_configured`). Top-level keys are unchanged.
`createJobQueue(...).enqueueRun({ workspaceId, runId, idempotencyKey? })` is the in-process API for the next tickets
(AGO-167 agent loop, AGO-160 claims, AGO-93 schedules). It throws `RunNotQueueableError` for a run that is missing,
in another workspace, or not `queued`, and `QueueUnavailableError` before the queue is up.

## Database changes
`supabase/migrations/20261107010001_ago_151_pgboss_schema.sql`: `create schema if not exists pgboss`, revoke all
from `public`, `anon`, `authenticated`, `service_role`, and no default privileges for them. `pgboss` is not in
`api.schemas`, so PostgREST never serves it. pg-boss's tables are third-party internals (not `workspace_id`
tables): isolation is by schema and grants, and the job payload carries `workspace_id` + `run_id` only.
The AGO-107 catalog test enumerates `public`/`graphql_public`, so it is unaffected and passes.
Rollback: `supabase/rollbacks/20261107010001_ago_151_pgboss_schema.down.sql` (`drop schema pgboss cascade`; drops
queued jobs - local data). Verified: rollback then re-apply on the local stack.
The worker connects as the `DATABASE_URL` owner role, which must be able to `create` objects in `pgboss`
(true locally and for the owner role of a managed database).

## Known limitations
- Nothing consumes jobs until AGO-167 passes a `runExecutor` (see D7).
- Re-running a run that ended `failed` needs a redrive/reset step (set the run back to `queued`, then enqueue) - not built.
- Dead-lettered jobs are visible (count in `/health`, rows in `pgboss.job`) but there is no UI or alert yet (AGO-83 health page).
- Depth counts come from `pgboss.job`; with very large retained history the `state in (...)` aggregate should be
  watched (pg-boss deletes completed jobs after 7 days by default).
- `.env.example` is not updated (not editable by this worker): add `QUEUE_CONCURRENCY` and `QUEUE_SHUTDOWN_TIMEOUT_MS`
  if the coordinator wants them listed. Both are optional with defaults.

## Fix round 1: no EXECUTE on pgboss functions
Postgres lets PUBLIC execute new functions by default, and pg-boss creates six (create_queue, delete_queue, job_now, job_table_format, job_table_run, job_table_run_async). Schema USAGE was already denied, so access was never effective, but the privilege itself is now removed too. The migration revokes it (existing functions plus default privileges), and because a schema-scoped default privilege cannot undo the built-in PUBLIC default, the worker also runs the idempotent `revoke execute on all functions in schema pgboss ...` after `boss.start()` (`apps/worker/src/queue/pgboss-hardening.ts`). Chosen over vendoring pg-boss's DDL into the migration, which would drift from pg-boss's own upgrades. Rollback is unchanged (dropping the schema removes everything).
