## Overview
A member submits a goal (AGO-113); the database also creates a task "Plan goal: ..." for the workspace's Manager. This
ticket lets the Manager run on that task, read the goal and **propose tasks with briefs, suggested owners and
dependencies**. The tasks land in the **Inbox** column; a person (or a later assignment step) decides who really starts
them. The Manager coordinates only: it cannot create or hire agents.

## Acceptance criteria (verbatim)
- [ ] Manager output creates tasks in Inbox with briefs
- [ ] Created tasks assign only to existing, non-archived agents
- [ ] Manager cannot create or hire agents
- [ ] Tests pass, no regressions, PR reviewed and merged, docs updated (see Definition of Done)

Comment on the ticket (AGO-113 note): `goals.text` is untrusted. Pass it through `wrapUntrusted` (AGO-23) when the
Manager reads it; never put it in the system prompt.

## Implementation details
**Tools.** Two worker tools, `read_goal` (returns the linked goal text as a tool result, which the context builder wraps with `wrapUntrusted`) and `propose_tasks` (`apps/worker/src/manager/`), capability `tasks.manage` (tier 1, already on
the Manager template), so it passes the policy engine like every tool. Input (Zod, strict): `goal_id`, and 1..12 items
`{ ref, title (<=300), brief (<=4000), suggested_agent_id?, depends_on: ref[] }`. `ref` is a local label so items can
name each other; a dependency may only name an EARLIER item of the same call, so there is no cycle or self reference by construction.

**Where the rules live.** The worker validates with Zod and a pure `planGoalTasks` function (DAG, limits,
suggested agent exists and is not archived and is not the Manager itself). The database is the enforcement boundary: a
new `SECURITY DEFINER` function `create_goal_tasks(workspace, run, goal, items jsonb)` (service_role only, same
convention as AGO-81/AGO-160) re-checks everything and writes all tasks in one transaction (all or nothing).

**What the function enforces (never trusts the caller).** The run's agent is read from the run and must be an active
agent whose role is `Manager`; the run's task must be linked to the goal (`tasks.goal_id`) so a Manager cannot split a
goal it was not asked to plan; the goal is in the same workspace; every `suggested_agent_id` is an existing,
non-archived agent of that workspace; the requester (human) is copied from the run's task `created_by`, never from
input; a cap of 12 tasks per call and 24 per goal.

**Inbox, owner and dependencies (the one design choice).** The board puts a task in Inbox only when it has **no agent**
(`derive-board`: "no agent, nothing running"). So created tasks have `agent_id = null` and `status = 'todo'`, and the
suggested owner is stored in a new column `tasks.suggested_agent_id` (nullable, composite FK to agents, `on delete set
null`), dependencies in `tasks.depends_on_task_ids uuid[]`. A suggestion is advice, not an assignment: nothing runs, no
claim, no budget is spent. Turning a suggestion into an assignment stays with a person (follow-up). This satisfies AC1
(Inbox) and AC2 (the only agent reference is validated against live agents) together.

**Brief.** `tasks.description` holds the brief the Manager wrote. It is model output and is **untrusted data** for the
agent that later reads it (AGO-81 rule), and is shown as plain text.

**Untrusted goal text.** The Manager's prompt builder loads `goals.text` for the goal linked to its task and passes it
through `wrapUntrusted` into the user message; the system prompt is unchanged (test: a goal containing a fake closing
tag or an instruction stays inside the block and the system prompt never contains it).

**Manager cannot create or hire agents.** No tool that creates, imports or hires an agent exists in the worker
registry and none is added. `propose_tasks` takes agent ids only to reference existing ones; an unknown id makes the
whole call fail (`unknown_agent`), it never creates one. The database function has no insert into `agents`, and a test
asserts the Manager's offered tool list and the function body reach no agent-writing path.

**Events.** None new: the tasks themselves are the trail (`goal_id`, `created_by`), and a new run-event type would touch the shared event schema and office reducer (deviation, 2026-11-21).

## Boundaries
- **Always:** scope by `workspace_id`; policy check before the tool runs; Zod at the boundary; Manager identity and
  agent liveness checked in SQL; goal text only inside `wrapUntrusted`.
- **Ask first:** the migration (schema slot from the orchestrator), any change to `derive-board`, the Manager template.
- **Never:** create or hire agents; assign (`agent_id`) a task; start a run or claim for a proposed task; put goal text
  in the system prompt; let input name the requester; write tasks outside the function.

## API changes
None over HTTP. New agent tool `propose_tasks` (worker). No web UI change (tasks appear in the existing Inbox column).

## Database changes
One migration `<timestamp>_ago_117_goal_task_proposals.sql` with a down script in `supabase/rollbacks/`:
`tasks.suggested_agent_id`, `tasks.depends_on_task_ids`, CHECKs (no self dependency, max 12 deps), function
`create_goal_tasks`, grants revoked from `public`, `anon`, `authenticated`; execute for `service_role` only. New
columns are in no column grant for `anon`/`authenticated`. pgTAP tests for the grants, isolation between workspaces,
archived or foreign agents, a non-Manager caller and a goal not linked to the run's task. Needs the **schema slot**.

## Known limitations
- Suggested owners are not assignments; nobody is notified and the web UI does not show the suggestion yet.
- Dependencies are stored and validated but nothing blocks a task on them yet (a scheduler ticket would).
- Re-planning the same goal adds tasks (cap 24 per goal); there is no dedupe or "replace plan".
- Manager output quality (are the tasks good) is not tested beyond shape; the model call is mocked in tests.
