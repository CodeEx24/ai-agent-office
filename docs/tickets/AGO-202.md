# AGO-202 - Fix flaky AGO-151 job-queue integration tests under full-suite load

## Overview
Jira: [AGO-202](https://stratyge.atlassian.net/browse/AGO-202) (Bug), wave 2, follows AGO-151.

The AGO-151 live-DB tests (`apps/worker/src/queue/job-queue.integration.test.ts`,
`scripts/ago-151-acceptance.test.mjs`, `scripts/ago-151-concurrent-start.test.mjs`) failed intermittently
(a different test each time) when the full `pnpm test` ran with `RUN_DB_TESTS=1`, and passed alone.

Acceptance criteria and where they are proven:

| AC | Proof |
|---|---|
| Root cause identified and documented | "Root cause" below |
| Each suite isolates its queue state and DB suites run in a safe pool configuration | Unique queue per suite ("Implementation details"); the DB suites already run serially with `RUN_DB_TESTS=1` (`vitest.scripts.config.mjs`, AGO-201) |
| Full `pnpm test` with `RUN_DB_TESTS=1` passes 5 times in a row | "Testing notes" (five runs, each holding the db lock `AGO-202`) |
| No assertion weakened; CI stays green | The diff touches no assertion and skips no test; CI on the PR |

## Root cause
All three suites, and every worker process they spawn, used the **one global pg-boss queue `agent-run`
(and `agent-run-dead`) on the one shared local database**. Each suite also runs
`delete from pgboss.job where name in ('agent-run', 'agent-run-dead')` before each test, and asserts exact
queue depth (`queued: 2, dead_letter: 1`) and "executed exactly once".

1. **Shared queue state across processes.** Any other process attached to that database with a consumer on
   `agent-run` (another suite's spawned worker that has an executor, or another ticket's worker or tester on
   the same Supabase stack, such as AGO-167 and AGO-141, whose workers reported the flake) competes for the
   same jobs. It steals a job (the asserting suite sees 0 executions or a missing retry), or it breaks the
   depth and count assertions, and its purge deletes the other suite's in-flight jobs. Which test breaks
   depends on timing, so a different test fails each time and a lone run passes.
2. **Turbo replayed test results.** `turbo run test` cached the `test` task, so a "green" `pnpm test` could be
   a replay of an old log (`FULL TURBO`) that ran no live-DB test at all, and a replay recorded while the
   database was down (every live test skipped) counted as a pass. The cache is shared across worktrees. A
   proof run is only meaningful if the tests actually execute.
3. **Not a cause (checked):** Vitest file parallelism. With `RUN_DB_TESTS=1` the scripts suites already run one
   file at a time (AGO-201), and `apps/worker` has a single live-DB test file, so there is no pool overlap to
   remove. No timeout was changed.

A separate observation from the first reproduction run: `ago-141-rollback` failed because the shared database
schema did not match this branch (another ticket had reset or migrated it). That is the shared-stack protocol
(reset under the lock before a DB run), not a queue race. The proof runs start from `supabase db reset` under
the lock.

## Implementation details
- `run-job.ts`: `runQueueNames(queueName?)` returns `{queue, deadLetter}`. The default is the production
  `agent-run` / `agent-run-dead`; a custom name gets `<name>-dead`.
- `job-queue.ts`: new optional `queueName` in `JobQueueOptions`, used everywhere the constants were.
  Production never sets it, so behaviour is unchanged.
- `main.ts`: `StartWorkerOptions.queueName`, passed through (tests only).
- Each suite owns a unique queue (`agent-run-test-<id>`, `agent-run-ago151-<id>`, `agent-run-ago151-cs-<id>`).
  The integration test passes it to `createJobQueue`; the script suites pass it to spawned processes as
  `QA_QUEUE_NAME`, which `scripts/fixtures/ago-151-proc.mjs` forwards. Purge, depth and "exactly one job"
  assertions are scoped to that queue, and each suite deletes its queues in `afterAll`
  (`pgboss.delete_queue`) so names do not pile up.
- The PostgREST "pgboss is not exposed" security test keeps posting a job named `agent-run`; it only proves
  the API roles are refused, nothing is written.
- `turbo.json`: `test` has `cache: false`, so `pnpm test` always executes the tests. CI has no turbo cache, so
  CI time is unchanged.
- `run-job.test.ts`: unit tests for `runQueueNames`.

### Decisions taken (no human at the keyboard; recommended option picked)
| Decision | Options | Chosen and why |
|---|---|---|
| How to isolate queue state | (a) unique queue name per suite, (b) per-suite cleanup only, (c) one global serial lock | (a), preferred in the brief: it removes the shared state, so it also protects against other worktrees' workers, which cleanup and pool settings cannot. (b) still shares the queue; (c) cannot stop other tickets |
| Product code change | add `queueName` option vs reach into pg-boss from tests | Add the small optional `queueName` option: the queue name is otherwise a module constant, and the spawned `startWorker` process has no other seam. Default unchanged |
| Pool config | force a serial Vitest pool for all DB suites vs leave | Leave: already serial under `RUN_DB_TESTS=1` (AGO-201) and only one worker file touches the DB, so a change would be a no-op |
| Turbo cache | `cache: false` for `test` vs add env/inputs to the hash | `cache: false`: database availability is not an input turbo can hash, so any hash would still replay a stale skip |
| `ago-151-rollback` suite | give it a unique queue vs leave | Leave: it drops the whole `pgboss` schema by design and must run alone under the lock |

## API changes
None. `JobQueueOptions.queueName` and `StartWorkerOptions.queueName` are optional, internal and test-facing.

## Database changes
None. No migration and no schema change (the schema slot was not used). Tests create and delete pg-boss queue
rows under unique names.

## Dependencies on other tickets
AGO-151 (the job queue and its tests). `main.ts` and `job-queue.ts` may also be edited by AGO-167; the change
there is a few lines, so a rebase conflict should be trivial.

## Known limitations
- Isolation covers the AGO-151 queue suites. The `ago-143` and `ago-164` acceptance tests spawn workers
  without an executor (nothing consumes), so they stay on the default queue.
- Tests that mutate shared database state (`*-rollback`, `db reset`) still need the db lock and a database at
  this branch's migration level.
- A crashed run can leave an `agent-run-test-*` or `agent-run-ago151-*` queue row. It is harmless and removable
  with `select pgboss.delete_queue('<name>')`.

## Testing notes

  `test` task is no longer cached), then release. The five consecutive runs are reported in the PR.
- Unit: `run-job.test.ts` ("run queue names").
