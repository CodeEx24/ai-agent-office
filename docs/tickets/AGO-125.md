## Implementation details
One migration, `supabase/migrations/20261106140001_ago_125_capability_catalog.sql`, with its rollback in `supabase/rollbacks/`.

**`public.capabilities`.** `id`, `workspace_id` (cascade), `key` (lowercase dotted, regex check, unique per workspace), `name`, `description`, `tier` (0 to 4), `scope` (`workspace | agent | external | sandbox`), `default_mode` (`automatic | approval`), `enabled`, timestamps. `unique (workspace_id, id)` for future composite FKs. It is separate from `agent_capabilities` (what a human granted to one agent); linking them is a follow-up.
- `capabilities_high_tier_never_automatic` CHECK `(tier < 3 or default_mode = 'approval')`: tier 3 and 4 can never be automatic, **in data**, for every role including `service_role`.
- RLS, per command, AGO-107 pattern: `capabilities_select_viewer` (any member or viewer) and `capabilities_update_owner` (owner only). No INSERT or DELETE grant for anyone.
- Grants: SELECT; UPDATE `(enabled, description)` only. `key`, `name`, `tier`, `scope`, `default_mode` and `workspace_id` are in no INSERT or UPDATE grant, so only a migration can change them, and an owner can never lower a tier or flip a default through the API.
- Seeding: `private.seed_workspace_capabilities(workspace_id)` (SECURITY DEFINER, `search_path = ''`, execute revoked from everyone, `on conflict do nothing`) inserts the 12 starters. The migration backfills all existing workspaces; `private.seed_capabilities_for_new_workspace()` on an AFTER INSERT trigger on `workspaces` covers new ones (seed data and onboarding included, so `pnpm db:seed` stays green with no change to `seed.sql`).

**Shared.** `packages/shared/src/capabilities/`: `capability-schemas.ts` (tier, scope, default mode, key, `capabilitySchema`, `listCapabilitiesQuerySchema`, response schema, `isAllowedDefaultMode`; the tier 3+ rule is also enforced in Zod) and `starter-capabilities.ts`. Exported from `@ago/shared`.

**Read API.** `apps/web/src/features/capabilities/capability-catalog.ts` (`import "server-only"`): `listCapabilities(workspaceId)` runs `requireWorkspaceRole(workspaceId, "viewer")`, reads through the signed-in user's Supabase client (so RLS applies as well), orders by tier then key, and parses every row with `capabilitySchema` (a stored row that breaks the schema fails closed). `apps/web/src/app/api/capabilities/route.ts`: `GET /api/capabilities?workspace_id=<uuid>`, input validated with `parseInput`, `Cache-Control: private, no-store`. 401 signed out, 403 not a member, 400 bad input, 500 `catalog_unavailable` with no detail. There is no write route (and so nothing for an agent token to call).

### Decisions taken (no human at the keyboard; recommended option chosen each time)
| Decision | Chosen | Why |
|---|---|---|
| Master List missing | Propose 12, ask the coordinator, use the confirmed list as v1 source of truth | Cannot invent silently; one amend point (see Overview). Confirmed by the coordinator. |
| Global vs per-workspace catalog | Per workspace, seeded by backfill + trigger | The AGO-107 catalog test requires `workspace_id` and an index led by it on every public table; per-workspace rows also let an owner disable a capability for their workspace without affecting others. |
| Tier 3 as well as 4 never automatic | CHECK `tier < 3 or default_mode = 'approval'` | The ticket says Tier 4; the coordinator amended it to tier 3+ to match CLAUDE.md "agents never act alone on Tier 3/4". A stricter rule still satisfies AC2. |
| Where AC2 is enforced | CHECK constraint on the table (not a trigger, not app code) | Declarative, cannot be bypassed by any role or code path, and a trigger would add a function to audit. Zod repeats the rule at the API edge. |
| Who writes | Owners, `enabled` and `description` only; tier/scope/default/key by migration only | Humans decide, and an owner cannot loosen risk through the API. Coordinator amendment. |
| Insert and delete | No grant at all | The catalog is system data. New starters arrive by migration (and the trigger). Nothing to delete: disable with `enabled`. |
| Read API location | Next route handler `GET /api/capabilities` + server-only data layer | Matches "read API through the workspace-scoped data layer"; reuses `requireWorkspaceRole` and `parseInput`. No new dependency. |
| Query parameter | `workspace_id` (snake_case, strict) | Matches the Data API naming the rest of the app uses; unknown params are rejected. |
| Keys | Lowercase dotted `domain.action`, regex-checked in SQL and Zod | Stable identifiers for the policy engine (AGO-34) and packs; same shape in both layers. |
| Link to `agent_capabilities` | Not added | A FK from `agent_capabilities.capability` to the catalog would change AGO-74's table and its tests; follow-up. |
| Pagination | None | The catalog is small and bounded (12 per workspace); response is one array. |

## API changes
New: `GET /api/capabilities?workspace_id=<uuid>` -> `{ capabilities: Capability[] }` (see `listCapabilitiesResponseSchema`). Auth: session cookie; viewer or higher in that workspace. Read-only. Data API: `authenticated` gets SELECT and UPDATE `(enabled, description)` for owners on `capabilities`; `anon` nothing.

## Known limitations
- The Master List is not in the repo; the 12 are the coordinator-confirmed v1 list.
- No UI. The ticket asks for storage and a read API only; the agent wizard (AGO-141) is the consumer.
- `agent_capabilities.capability` is still free text and is not tied to the catalog (follow-up).
- An owner can disable a capability (`enabled = false`), but nothing enforces `enabled` yet: that belongs to the policy engine (AGO-34).
- A workspace created while the trigger is missing (never, after this migration) would have no catalog; re-running the seed function repairs it.
