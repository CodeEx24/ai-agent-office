# AGO-102 - US-014 Make run_events append-only

## Overview
`run_events` (AGO-74) becomes an append-only log enforced **in the database**, plus a per-run increasing sequence number. Jira: AGO-102, epic EP-01 (Data and auth), wave 1, risk high (data model, audit trail, security invariant "run_events append-only"). Blocked by AGO-74 (done). Local Supabase only; nothing touches a hosted project.

Acceptance criteria:
1. Given any role, when an update or delete on `run_events` is attempted, then it is rejected.
2. Inserts carry a per-run sequence number that must increase.
3. Tests pass, no regressions, PR reviewed and merged, docs updated.

## Implementation details
Two migrations, each with a rollback in `supabase/rollbacks/`: `20261105090001_ago_102_run_events_append_only.sql` (guards and per-run seq) and `20261105100001_ago_102_run_events_restrict_delete.sql` (fix round 1: no removal path at all, see below).

**Append-only (defence in depth).** RLS is not enough: `service_role` bypasses it and RLS does not govern TRUNCATE.
1. Privileges: `UPDATE`, `DELETE`, `TRUNCATE`, `TRIGGER`, `REFERENCES` (and column-level UPDATE) revoked from `PUBLIC`, `anon`, `authenticated`, `service_role`.
2. `private.run_events_block_change()` is attached as a `BEFORE UPDATE OR DELETE` row trigger and a `BEFORE TRUNCATE` statement trigger. It raises `42501` for every role, including `service_role` and the table owner. All three triggers are `ENABLE ALWAYS`, so they also fire under `session_replication_role = replica`.
3. **No removal path at all (fix round 1).** The first migration let the workspace FK cascade remove events (a "workspace gone" exception in the guard). Review rejected that: the append-only invariant wins, and `service_role` could erase a tenant's log. The forward migration `20261105100001_ago_102_run_events_restrict_delete.sql` makes `run_events.workspace_id -> workspaces` and `(workspace_id, run_id) -> runs` `ON DELETE RESTRICT` and removes the exception, so the guard raises `42501` for every row delete. Removing a workspace or run that has events fails with `23503`; one without events still goes (its other data still cascades). Erasure of events is a deliberate human-only path deferred to **AGO-147**. AGO-74's merged migration is untouched.

**Per-run sequence.** `seq` is no longer the global identity. It is `bigint not null default 0 check (seq > 0)` with `unique (workspace_id, run_id, seq)`. `private.run_events_before_insert()` (BEFORE INSERT, `SECURITY DEFINER`, `search_path = ''`) takes `pg_advisory_xact_lock(hashtextextended('run_events:' || run_id, 0))`, reads `max(seq)` for the run, and then:
- `seq` omitted, null or `0`: assigns `max + 1`;
- `seq` given and `<> max + 1`: raises `23514` (duplicate, out of order, negative, or a gap; a huge value could otherwise overflow bigint and brick the run);
- `seq` given and `= max + 1`: accepted.
Inserts require READ COMMITTED isolation (`25000` otherwise): under REPEATABLE READ the `max()` would read a stale snapshot.

The lock serializes concurrent inserts for the same run only; different runs do not block each other. `SECURITY DEFINER` makes the `max()` independent of the caller's RLS (AGO-107 policies would otherwise hide rows and give a wrong max). The unique constraint is the backstop.

**How a privileged actor could still change it.** A superuser (or the table owner via DDL) can `ALTER TABLE ... DISABLE TRIGGER`, drop the triggers, or re-grant privileges. That is by design the migration path: schema changes go through reviewed migrations only, never at runtime. The application roles (`anon`, `authenticated`, `service_role`) cannot do any of it.

### Decisions taken (recommended option chosen, no human available)
- **Triggers plus revokes, not rules or RLS only.** Triggers raise for `service_role` and the owner; privileges give a first, cheap rejection; RLS is irrelevant for UPDATE/DELETE once both exist.
- **`max + 1` under an advisory lock, not a per-run sequence object.** No objects per run, race-safe, and the assigned value is validated by the same path as caller-supplied values. The sequence is strictly increasing and gap-free; callers may pass exactly `max + 1` or omit it.
- **Omitted/null/`0` means "assign next".** `default 0` keeps `seq` optional in the generated insert types (`seq?: number`) so callers do not have to compute it; `check (seq > 0)` means a stored `0` is impossible.
- **RESTRICT, not a cascade exception (fix round 1).** An earlier version let the workspace cascade through by checking that the workspace row was gone. Replaced by `ON DELETE RESTRICT` on both parents plus a guard with no exception, so the invariant has no loophole; tenant erasure becomes an explicit human-only path (AGO-147).
- **`unique (workspace_id, run_id, seq)`** instead of `(run_id, seq)`: keeps the tenant column leading, replaces the AGO-74 index (same columns) so there is no duplicate index.
- **No actor column** (AGO-74 follow-up asked for a decision): out of scope here; the typed emitter (AGO-164) decides what an event records, a column can be added later by one additive migration.
- **Vitest concurrency test uses `docker exec psql`**, no new dependency (no pg driver in the stack), gated by `RUN_DB_TESTS=1` because CI has no database yet (AGO-92).

## API changes
None. Generated insert types: `run_events.seq` is now `number` and optional (was `never`, identity).

## Database changes
Migrations and rollbacks above. `pnpm db:types` regenerated `packages/shared/src/db/database.types.ts`.
Rollback: apply the newest `.down.sql` first (`20261105100001_...restrict_delete.down.sql` restores the workspace cascade and the "workspace gone" guard exception), then `20261105090001_...append_only.down.sql` (drops the three triggers and two functions and the constraints, restores `seq` as a global identity starting after the current max, restores the old index and the `service_role` privileges), delete the migration row from `supabase_migrations.schema_migrations`, or just `pnpm db:reset` on the previous commit. Existing rows are renumbered per run by the migration (none exist outside tests).

## Dependencies on other tickets

## Known limitations
- A superuser can still disable the triggers (see above); detecting that belongs to AGO-137.
- Removing a workspace or run that has events is refused (`ON DELETE RESTRICT`); events are never erased by the app. Erasure/retention is a human-only path, AGO-147. Archiving a workspace is the supported way to retire it.
- Inserting events for several runs in one transaction should use a consistent run order (per-run advisory locks, deadlock `40P01` otherwise).
- Removing a tenant that has events needs the AGO-147 erasure path (a privileged, human-approved procedure); until then it is impossible, by design.
- `truncate public.workspaces cascade` is rejected because it reaches `run_events` (truncate trigger).
- `pnpm test:e2e`: no UI or route was touched.
