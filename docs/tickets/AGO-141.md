# AGO-141 - US-024 Build the agent creation wizard

## Overview
Epic EP-03 (Skills and capabilities), wave 2 (Agent Runtime + Guardrails), workstream WS-C (Web App and UX), risk tier **high** (data model, authorization, human-in-the-loop surface). Jira: https://stratyge.atlassian.net/browse/AGO-141. Blocked by AGO-125 (capability catalog), AGO-128 (skill library), AGO-82 (roles) and AGO-115 (shadcn/ui), all done.

"As an owner, I want a wizard with name, role, model, prompt, skills, capabilities and daily budget so that I can hire an agent in under two minutes."

Acceptance criteria (verbatim):
- Given valid inputs, when I finish the wizard, then an agent is created in Strict mode
- A new agent can be created in under two minutes in a timed test
- Validation errors name the field
- Tests pass, no regressions, PR reviewed and merged, docs updated (see Definition of Done)

The wizard never grants a permission on its own: a skill is know-how, a capability is chosen by the owner, and a Tier 3 or 4 capability **always needs approval** (CLAUDE.md: a human is always in the loop).

## Implementation details
**Shared** (`packages/shared/src/agents/`):
- `agent-limits.ts` is **zod-free** (like `skill-limits.ts`, AGO-128) so the client wizard can import it from `@ago/shared/agent-limits` without pulling zod, whose JIT feature detection needs `unsafe-eval`, into the browser bundle (CSP). It holds the limits, the static model allowlist, the field labels, one message per rule (each names its field), `parseDailyBudget` (dollars to cents, no floats), `checkAgentDraft` (client checks) and the wizard steps.
- `agent-schemas.ts` is the zod schema used by the server action (`createAgentSchema`, a strict object: no `mode`, `status` or `tier` field exists), `resolveCapabilityGrants` (checks the choices against the catalog; a Tier 3 or 4 capability may never be automatic) and `fieldErrorsFromIssues`. A test keeps the client checks and the schema in step.

**Web** (`apps/web/src/features/agents/`):
- `agent-library.ts` (server-only): `listAgents`, `getAgentWizardOptions` (owner only: the workspace's skills and enabled capabilities), and `agentCreator.createAgent` which requires the owner role, resolves the grants against the catalog, then makes **one** `create_agent` RPC call. The `AgentCreator` interface is the seam the action is tested through.
- `actions.ts` (`"use server"`, one endpoint): `parseInput(createAgentSchema, ...)` then `createAgentWith`. `create-agent.ts` holds the error mapping so it can be unit tested without becoming an endpoint.
- `AgentWizard.tsx`: five steps (Basics, Skills, Capabilities, Budget, Review) in one client component, so the draft survives Back and Next. Errors are `role="alert"` next to their field, wired with `aria-describedby`/`aria-invalid`, and focus moves to the first invalid field (server refusals jump to the step that owns the field). Next is a submit button, so Enter moves on. Tier 3/4 capabilities show "Needs approval every time" and offer no "automatic" choice.
- Routes: `/app/agents` (list, viewers and up, "New agent" link for owners) and `/app/agents/new` (owners only; anyone else is redirected to the list). A link to Agents was added to `/app`.

**Database** (draft, see below): `agents.role/model/prompt/daily_budget_cents`, `agent_capabilities.mode`, owner-only `agents` insert, and `public.create_agent(...)`.

### Decisions taken (no human at the keyboard; recommended option chosen each time)
| Decision | Chosen | Why |
|---|---|---|
| Schema slot | Asked the coordinator; AGO-151 holds it. Built every non-schema part first; the migration stays a draft until the slot is granted | One schema-changing ticket in flight (CLAUDE.md). |
| Where role, model, prompt live | New columns on `agents` | Typed, queryable, length-capped; packing them into `description` text is untyped. Approved by the coordinator. |
| Daily budget | Column `agents.daily_budget_cents` (integer cents, 1 to 5000), default in the UI $5.00 | `budgets_usage` is a per-period usage ledger written by the runtime; a daily limit is a setting of the agent. Integer cents avoid float rounding. |
| Workspace budget cap | Platform constant `AGENT_DAILY_BUDGET_MAX_CENTS` = $50.00, repeated in the DB CHECK | No per-workspace cap row exists yet; a budget above it is refused, never silently lowered. |
| Model choice | Static allowlist in `packages/shared` (4 models), **no preselected model** | No API call, and the wizard never makes a paid choice for the user. |
| Capability mode | New `agent_capabilities.mode` (`automatic`/`approval`) with `CHECK (tier < 3 or mode = 'approval')` | "Always needs approval" must be recorded and enforced by the database, not only the UI. |
| Tier source | Read from the workspace catalog on the server and again inside `create_agent`; the request never carries a tier | A tampered request cannot lower a tier. |
| Atomic create | One `SECURITY INVOKER` function `create_agent` | One transaction (agent + skills + grants); RLS stays the enforcement point and no privilege is widened. |
| Owners only | `agents_insert_owner` policy replaces `agents_insert_member`; the function also checks the role | Matches the ticket ("As an owner") and CLAUDE.md. Existing tests that encoded "a member can create an agent" are updated. |
| Strict mode | `mode` is in no grant and not a field of the schema; the column default is the only way | An agent can never start with more autonomy. |
| Client validation | Zod-free helpers with the same messages; server uses the zod schema; a test compares them | Avoids zod in the client bundle (CSP, AGO-128). |
| Draft between steps | Held in the single client component | No storage, nothing to leak; survives Back/Next. |
| Redirect after create | `/app/agents` (the list shows the new agent as Strict) | There is no agent detail page yet (edit is AGO-89). |

## API changes
No new HTTP routes. New pages `/app/agents` and `/app/agents/new` (session cookie; viewer and up read, owner creates). One server action, `createAgentAction`, validated with `parseInput` and gated by `requireWorkspaceRole(..., "owner")`. Data API: `authenticated` may call `rpc/create_agent`; `agents` insert is owner-only on columns `(workspace_id, name, description, role, model, prompt, daily_budget_cents)`; `agent_capabilities` insert is owner-only and now includes `mode`.

## Database changes
Draft migration `supabase/migrations/20261107120001_ago_141_agent_wizard.sql` (renamed to the next free timestamp when the slot is granted), rollback `supabase/rollbacks/20261107120001_ago_141_agent_wizard.down.sql`:
- `agents`: `role`, `model`, `prompt` (checked, length-capped), `daily_budget_cents` (1 to 5000).
- `agent_capabilities`: `mode` and `agent_capabilities_high_tier_never_automatic`.
- `agents_insert_owner` replaces `agents_insert_member`; insert grants re-issued per column.
- `public.create_agent(uuid, text, text, text, text, integer, uuid[], jsonb)`: owner check, budget range, skills must belong to the workspace, capability tier read from the catalog, automatic Tier 3/4 refused, pinned `search_path`, execute revoked from `public` and `anon`.
- `packages/shared/src/db/database.types.ts`: patched by hand to match until `pnpm db:types` can regenerate it from the applied migration.

## Known limitations
- No edit, duplicate or archive of an agent (AGO-89), and no agent detail page.
- The model list is static; adding a model is a code change.
- The budget cap is a platform constant until a per-workspace cap exists.
- The wizard keeps its draft in memory only: a page reload starts again.
- Agents created before this ticket have an empty role/model/prompt and no budget (null).
