## Overview
Before anything is imported, an owner uploads a pack and sees exactly what it would change. The preview writes nothing. It checks the file (size, JSON, agent count, depth, schema, secret scan, checksum), then lists per agent and per skill whether import would create, update or skip it, every capability with its catalog risk tier, Tier 3 and 4 flags, trifecta combinations, name conflicts, references to set up afterwards, and everything import would ignore and why. One code path serves the API route and the `pnpm pack:import` dry-run.

## Design
**Pure core (packages/shared, additive, node only because of the checksum):** `packs/agent-pack-import-preview.ts`, exported as `@ago/shared/pack-import-preview` (same pattern as `pack-export`). Two parts:
1. `inspectPackText(text)`: the pre-parse guard. Byte size limit (`MAX_PACK_BYTES`, 5 MiB), a linear string-aware scan of `{`/`[` depth (limit 12) that stops at the first breach, then `JSON.parse`, then cheap structural counts on the parsed value (agents, skills, notes over the schema caps; total node count limit) BEFORE the Zod parse. Rejections are `{ code, message }` with fixed messages; they never repeat pack text.
2. `buildImportPreview(pack, context)`: pure. `context` is plain data: existing agents and skills of the workspace, the capability catalog (key, tier, scope), the model allowlist, the budget cap. It returns the preview object below. No database, no network.

**Preview result** (`ImportPreview`):
- `importable`: false when any blocker exists. Blockers: checksum mismatch, unknown model, a trifecta combination that would remain after ignored capabilities are removed. (Import is all-or-nothing, so one blocker blocks the whole pack; the preview says which.)
- `checksum`: `missing | valid | mismatch` (reuses `verifyPackChecksum`).
- `agents[]`: name, `action: create | update | skip`, `conflict` (same name exists), reason, capabilities each with `name`, `scope`, `tier` (from the workspace catalog), `status: applied | ignored`, `ignoredReason` (`tier_3_or_4`, `unknown_capability`), flags `tier3plus` and `trifecta`; applied budget (cap rule), model check, mode note (`would land in Strict`), skills list.
- `skills[]`: name, `action`, `conflict`, version change.
- `references[]`: things to set up afterwards, by name only: `secret:<name>` refs per agent, capabilities that need an integration (`integration.*` keys), department names (no departments table yet, not applied), pack notes (counted, not imported yet).
- `ignored[]`: every item import would ignore and why (Tier 3+ capability, unknown capability, budget above the cap, autonomy mode other than Strict, department, notes).
- `summary`: counts per action, per tier, blockers.
Action rules: an agent name that is new is `create`; an existing name with the same role, model, thinking effort and prompt is `skip` (identical); an existing name that differs is `update` (a conflict, listed). Skills: new `create`; same name and same body `skip`; same name, different body `update`. Archived existing agents match by name too and are noted.

**Loader (server only, client passed in):** `apps/web/src/features/packs/preview-agent-pack-import.ts`. Reads, through the caller's RLS-bound client and scoped by `workspace_id`, named columns only: `agents` (name, role, model, thinking_effort, prompt, archived_at), `skills` (name, version, body), `capabilities` (key, tier, scope). SELECT only, no rpc, no insert, no function call. Then the pure core. Does not read credentials, identities, runs or budgets usage.

**Route:** `POST /api/agent-packs/import/preview`, thin. `rejectAgentCredential` first (human-only), `requireWorkspaceRole(workspace, "owner")` (owner decision a4; stricter than export, which allows members), called before the body is read. The body is the pack file itself as the request body with the workspace in a query parameter `workspace_id` (Zod on the query): so the size limit can be applied to the raw bytes before any JSON parse, using `Content-Length` and a counted stream read that stops at the limit. Content-Type must be `application/json` (415 otherwise, also blocks CSRF). Responses: 200 the preview (also when `importable` is false, because a blocked preview is still a preview), 400 bad query, 401 signed out, 403 not allowed or agent credential, 413 over the size limit, 415, 422 not a valid pack (list of at most 20 issues with a path, each message shortened, never echoing pack text), 500. `Cache-Control: private, no-store`.

**CLI:** `pnpm pack:import --workspace <uuid> --file <path> [--json]` is dry-run only in this ticket (AGO-194 adds apply). Signs in as the person exactly like `pack:export` (same env names), checks file size on disk before reading, runs the same loader and core. Prints a readable summary (or the JSON). Exit 0 importable, 1 blocked or failed, 2 bad usage. There is no apply flag; asking for one prints that applying is not available yet.

**Untrusted text:** pack text (prompts, skill bodies, notes) is never put into the preview. The preview carries names (bounded, control characters stripped), numbers and fixed reason codes, not bodies or prompts. Names are JSON data; any UI must render them as text.

## Boundaries
- Always: workspace_id scoping with RLS, human-only route, Zod at the boundary, named columns only, SELECT only, one shared code path, fixed messages that do not echo pack text.
- Ask first: a migration, any change to the pack schema, the trifecta lint or the capability catalog.
- Never: write to any table, log pack content, apply anything, touch approvals, budgets or the agent loop (AGO-58, AGO-40).

## Deviations from the accepted record
- 2026-11-14: the route role is `owner`, not `member` (owner decision a4).
- 2026-11-14: the loader reads each table in pages of 1,000 rows (PostgREST returns at most 1,000 rows per request), up to 20 pages, so a large workspace is not silently truncated.
- 2026-11-14: a department is both a reference (to set up afterwards) and an ignored item.
- 2026-11-14: `validatePackText` was added as the single validate step (guard, then schema) that the loader calls before it reads anything from the workspace.
- 2026-11-14: with the starter catalog the outbound leg of the trifecta (`message.send_outbound`, `integration.write`) is Tier 3 and therefore ignored, so a declared trifecta normally does not remain after ignoring; it is still flagged, and is a blocker only when it remains (tested with a lower-tier catalog).
