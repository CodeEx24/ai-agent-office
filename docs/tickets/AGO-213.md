# AGO-213 - Fix the pg-boss hardening race, run-failure event ordering and gate lock release

Ticket: https://stratyge.atlassian.net/browse/AGO-213
PRs: (pending)
Related: AGO-151 (pgboss hardening + grants migration), AGO-40 (PR #65) and AGO-37 (PR #70) are blocked on the local gate, AGO-86 holds the schema slot.

Type: Bug. Risk: medium, security surface (pgboss EXECUTE grants hardening). Wave 2. Human-merge path (`scripts/` changes).

## Overview
Local gates failed 8+ times on 2026-11-14 across AGO-40, AGO-37 and AGO-86. Each failing test passes alone; CI stays green. Three root causes on main plus load-sensitive waits.

## Acceptance criteria (verbatim from Jira)
- [ ] After N workers start concurrently on a fresh DB, no pgboss function grants EXECUTE to PUBLIC or API roles, including after pg-boss's async migrations finish. Proven by ago-151 passing 10/10 in loaded full-suite runs.
- [ ] `run.failed` is appended before (or atomically with) the run's failed status. Tests wait on the event, not the status.
- [ ] `checks.mjs` never releases a lock it did not acquire in that step. A test proves the caller's lock survives the pgTAP step.
- [ ] The listed timing-sensitive tests wait on conditions with load-tolerant budgets, not fixed short timeouts.
- [ ] The full local gate passes 3 runs in a row with 3 Orca workers active.
- [ ] Tests pass, no regressions, PR reviewed and merged, docs updated.

## Root causes (found by reading the code)
1. **Hardening race.** `connect()` in `job-queue.ts` calls `instance.start()` then `hardenPgbossFunctions(pool)` once. pg-boss 12 runs part of its migrations as background "bam" commands (`dist/bam.js`, started by `start()` with `setImmediate`, then every `bamIntervalSeconds`, default 60) and other workers' installs/migrations run concurrently. A function created or replaced after a worker's one-shot revoke keeps the default PUBLIC EXECUTE until some later worker hardens. `start()` returning does not mean pg-boss is done creating functions.
2. **Event ordering.** `run-processor.ts` `handleFailure` (final attempt) awaits `runs.markFinished(failed)`, then `dropCheckpoint()`, then emits `run.failed`. A reader that sees status `failed` can read events before `run.failed` exists. The `limit_reached` / `loop_detected` branches write their terminal event inside the loop first, so only the final-failure path is wrong.
3. **Lock release.** `pgtapStep` in `scripts/workflow/checks.mjs` runs `db-lock acquire <owner>`; for the same owner it exits 0 with "already held" and the `finally` then releases the caller's lock.

## Design
- **Event ordering:** emit `run.failed` first, then `markFinished(failed)`, then `dropCheckpoint()`. If the emit fails (already logged by the emitter) the run is still marked failed. `run_events` stays append-only. Test: a fake store records call order and asserts `run.failed` precedes the status write.
- **Lock release:** parse the acquire output; release only when it says "acquired by" (this step took it), never on "already held". The decision is a small exported pure function (`lockTakenByThisStep(output)`) with a unit test, plus a test with a stub `run` proving the release call is skipped when the lock was already held.
- **Waits:** replace fixed short timeouts and start deadlines in the named tests with condition-based polling and larger budgets (assertions untouched, worker count stays 10).
- **Hardening race:** see decision D1.

Conditions: the loop has a clear maximum wait; if grants remain at the end it throws (fail closed, the queue never runs unhardened, never log and continue); no migration, no schema slot. Extra test: create a pgboss function with a PUBLIC grant after start and prove the loop revokes it. | Owner, 2026-11-14 (via coordinator, standing rule: recommended option) |
| D2 | Record accepted with the D1 conditions added. | Owner, 2026-11-14 |

D1 options: (a) `ALTER DEFAULT PRIVILEGES` revoking EXECUTE from PUBLIC (needs a migration and the schema slot; in-schema default privileges cannot remove the global implicit PUBLIC grant, so it would have to be the role-wide form, which also changes every other schema the role creates functions in); (b) harden again after pg-boss's background migrations settle: wait until the `pgboss.bam` table has no `pending`/`in_progress` entries (via `getBamStatus()`), harden, then re-check until a verification pass finds no grants, bounded by a deadline; (c) both. Recommendation: (b), no migration, no schema slot, keeps the existing "no USAGE for API roles" layer.

## Boundaries
- **Always:** keep the revoke serialised behind the advisory lock; keep the schema closed to API roles; fail loudly rather than run unhardened.
- **Ask first:** any migration (schema slot is held by AGO-86), files outside the owned paths.
- **Never:** lower the 10-worker count, drop the grants assertion, skip a test, edit `scripts/db-lock.mjs`.

## Known limitations
The hardening settle loop is bounded; if pg-boss background migrations never settle, or grants remain at the end, the worker fails its start (and the queue's own start retry runs) instead of running unhardened.
**Residual risk (accepted):** a function pg-boss creates after the loop has finished keeps its default PUBLIC EXECUTE until the next worker start hardens again. The pgboss schema has no USAGE for the API roles (AGO-151 migration), so nothing is reachable in that window.
