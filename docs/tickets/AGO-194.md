## Overview
Apply a validated agent pack to a workspace. The dry run (AGO-193) already parses, migrates and plans; the apply
runs the same plan and writes it in one transaction.

Acceptance criteria (verbatim):
1. Every imported agent starts in Strict mode and probation, whatever the pack says
2. Capabilities of Tier 3 or higher, budgets above the workspace cap, policies, identities and credentials in a pack are ignored and reported; a human grants them later through the normal approval flow
3. Trifecta lint runs on each imported agent; a failing agent is imported disabled with the reason shown
4. Name conflicts follow the chosen rule: skip, rename, or create a new version; imported skills arrive as new versions, never silent overwrites
5. Import is one transaction (all or nothing), requires the owner role, rejects agent tokens, and writes an event with the pack checksum
6. Tests pass, no regressions, PR reviewed and merged, docs updated (see Definition of Done)

## What exists today (explored 2026-11-17)
- Pure plan: `buildImportPreview` / `validatePackText` (`packages/shared/src/packs/agent-pack-import-preview.ts`, node only). The loader `previewAgentPackImport` (`apps/web/src/features/packs/preview-agent-pack-import.ts`) reads agents, skills, capabilities as the caller. Route `POST /api/agent-packs/import/preview` (human-only guard, JSON check, owner role, size-limited body). CLI `pnpm pack:import` is dry run only; `--apply` prints "not available" (the CLI apply is AGO-195).
- Writers that exist: `create_agent` RPC (invoker, owner, strict by column default + insert guard, skills + capabilities in one transaction), `update_agent` (optimistic lock, trigger appends `agent_versions`), `archive_agent`. Skills: updating `skills.body` bumps `version` and a trigger appends `skill_versions` (AGO-128); no delete grant.
- `agents.mode` is in no column grant; an insert guard refuses any non-strict agent (AGO-99).
- `pack_events` (AGO-192) is append-only, written only by SECURITY DEFINER `record_pack_export`. Its `kind` check allows only `'export'` ("AGO-194 adds 'import' by widening the check") and requires 1..100 agent ids.
- The trifecta lint is TypeScript only (`packages/shared/src/agents/trifecta-lint.ts`); there is no DB backstop.
- There is **no "probation" concept anywhere** (no column, no doc). There is **no "disabled" agent state** except `archived_at`.
- The preview currently treats a trifecta that remains after dropping Tier 3+ as a **blocker** (`importable: false`). AC3 says such an agent is imported disabled instead.

## Design
One code path: `packages/shared/src/packs/agent-pack-import-plan.ts` (new, next to the preview) turns a validated pack + the same `PreviewContext` + a conflict rule into an `ImportPlan` (plain data: per agent `create | update | skip | rename`, its applied capabilities, applied budget, `disabledReason`, per skill the new version). `buildImportPreview` and the apply both call it, so the report the owner saw is what is applied (test: preview equals apply, on the same input). The CLI (AGO-195) and a later UI call the same loader.

Apply path:
1. `applyAgentPackImport(client, {workspaceId, text, onConflict})` (`apps/web/src/features/packs/apply-agent-pack-import.ts`): `validatePackText`, load the context exactly like the preview (reuse the loader, extract `loadPreviewContext`), build the plan, refuse when the plan has blockers (checksum mismatch, model not allowed), then call one RPC with the plan.
2. Route `POST /api/agent-packs/import?workspace_id=&conflict=skip|rename|new_version` (thin): `rejectAgentCredential` first, JSON content type, `requireWorkspaceRole(owner)` before the body is read, size-limited body, loader, RPC. 200 with the report, same status map as the preview, 409 for a stale plan.
3. RPC `public.import_agent_pack(p_workspace_id, p_checksum, p_plan jsonb)` (one transaction, so all or nothing): re-checks owner (`private.is_member(..., 'owner')`, `auth.uid()` set: an agent token has none), and re-derives what it can from its own tables instead of trusting the plan: tier from `capabilities` (Tier 3+ never granted), budget clamped to 1..5000, mode never set (column default + insert guard = Strict), existing names re-read under lock, every id resolved inside `p_workspace_id`. The plan can only make an import safer (extra `disabled` flag), never more privileged. It then writes agents, `agent_skills`, `agent_capabilities` (mode `approval`), skills (new version via the existing trigger), archives disabled agents, and appends exactly one `pack_events` row with the checksum.
4. Pack text stays data: no prompt, skill body or note is ever put in an error, event or log line; messages use `safeText` and fixed codes. Notes are not imported (AGO-198).

Decisions this design rests on (the table lists who decided; open ones are asked):
- **Conflict rule** is one value for the whole import: `skip` (default, leave the existing agent / skill), `rename` (create `<name> (imported)`, then `(imported 2)`, ...; trimmed to the 120 char cap), `new_version` (update the existing agent through the same version trigger as `update_agent`: role, model, effort, prompt, budget; add missing skills and capabilities; never remove, never touch `mode`). Skills: a changed body is always a new `skill_versions` row, never an in-place rewrite; identical body is skipped; under `rename` a skill is created as a new skill.
- **Never applied, always reported:** Tier 3+ and unknown capabilities, budgets above the cap (the default is used), non-Strict modes, departments, secret references, integrations, notes. Policies, identities and credentials are not in the pack schema at all (strict schema rejects them; the secret scan rejects secret-shaped values).
- **Disabled** = archived (`archived_at`). An archived agent cannot receive tasks or be edited until an owner unarchives it, which is the "a human decides" step. The reason (a fixed code, `trifecta_combination`) is returned in the report and stored in the import event.
- **Probation** = Strict mode, no extra state (see question 1).
- **Preview change (AC wins):** a remaining trifecta stops being a blocker and becomes `importDisabled: { reason: "trifecta_combination", legs }` on the agent; other blockers (checksum, model) stay. The preview and apply report stay identical.
- A migration is needed (the all-or-nothing transaction and the event cannot be done from the client; PostgREST calls are separate transactions): see Database changes.

## API changes
`POST /api/agent-packs/import` (new, owner only, human only). Request: the pack file as body, query `workspace_id`, `conflict`. Response: the import report (same shape as the preview plus `eventId`, `created`, `updated`, `skipped`, `disabled`). The preview route and its response gain `importDisabled` on agents; the `trifecta_combination` blocker code is removed.

## Fix round 2 (tester round 1: CHANGES, 10 red tests)
The functional tester found three real bugs and some nits. The migration was edited in place (not yet merged); the tester's acceptance tests are unchanged.
- **Missing or null `action`** fell into the update or new-version branch (`NULL not in (...)` is unknown). The function now validates every agent and skill entry in a first pass, before any write: `action` must be an explicit string in the allowed set, else SQLSTATE 22023; the write loops use `if / elsif / else raise` (no fall through).
- **Trifecta on an update.** The planner lints existing capabilities UNION the pack's applied ones (the loader now also reads `agent_capabilities`); a union that completes the trifecta applies the update and sets `importDisabled` (`summary.disabled` counts it); the pack alone being a trifecta still skips the update. The function recomputes the trifecta from `agent_capabilities` after granting (key to leg mapping mirrors `trifecta-lint.ts`, commented in the SQL), archives the agent and records the effective reason in `detail`.
- **Hostile text.** NUL and lone surrogates (in a value or a field name) are refused in `validatePackText` with 422 `invalid_pack` and the field path, before any database call. jsonb cannot hold them either, so the function cannot be handed them; the apply layer also maps 22P02, 22P05 and 22032 to `invalid` instead of a 500. Decision: this changes the AGO-193 preview, which used to strip NUL from names; the matching AGO-193 acceptance case now asserts the refusal.
- **Nits.** `renamedCopyName` cuts on whole code points. Names in `pack_events.agent_names` and `detail` lose control, zero-width and direction-override characters. A budget must be a JSON integer (text, fractions: 22023) before any cast.
- Tests: `agent-pack-import-hardening.test.ts` (plan, rename, boundary), pgTAP `pack_import.test.sql` now 51 assertions. Loader tests updated for the extra `agent_capabilities` read and the `id` column.
- **Process note:** during this round the db lock I held went stale (over 60 minutes of editing) and was taken by AGO-71; one `supabase db reset` and pgTAP run overlapped with AGO-71's session before I noticed. The final runs were repeated under a freshly acquired lock.

## Fix round 3 (reviewers round 2: code, security, database CHANGES; the last round)
Items from the dispatch, each with its test:
- **(a) Mode on update.** `new_version` on an existing Standard or Relaxed agent sets it to Strict in the same transaction as the prompt replacement (CLAUDE.md: import always lands agents in Strict). Only when it is not Strict already (the log has `from_mode <> to_mode`). The `agents` mode log trigger records it (the caller is still `auth.uid()` inside the definer function), and `detail.agents[].mode_reset_from` (present only on a reset agent) plus `detail.modes_reset` record it. The dry run shows `resetsModeFrom` (loader now reads `agents.mode`). The plan carries no mode, so preview and apply cannot drift. Tests: pgTAP (relaxed to strict, log row, event detail, strict agent adds nothing), plan tests (preview shows the reset, plan identical), loader test, live test (preview == apply, log and event).
- **(b) Constraint drop.** The `pg_constraint` loop is gone: exactly `pack_events_kind_check` and `pack_events_agent_ids_check` are dropped by name. The AGO-192 `cardinality(agent_names) = cardinality(agent_ids)` check is untouched; a guarded `do` block restores it where an earlier draft of this migration had dropped it. The rollback restores exactly what up changed. Tests: pgTAP (the check exists, and a mismatched insert is refused by it), the rollback test (exact drop list; the check exists before, after rollback and after re-apply).
- **(c) Paging.** `agent_capabilities` is read ordered by `agent_id`, then `capability`.
- **Smaller.** One invisible-character set (`PACK_INVISIBLE_RANGES`, adds U+00AD, U+034F, U+061C, U+180E, U+2060-2064 and the tag characters) used by the TypeScript helper and by the SQL scrub written with unicode escapes; a test parses the SQL class and compares. The first pass validates role, model, prompt and thinking effort as strings, array size (50) and element type, and `disabled_reason` (null or `trifecta_combination`), all 22023. The RPC call is typed (`ImportPlan` is a type alias, assignable to `Json`; the `as unknown as` cast and the local client interface are gone). The stale plan comment and the exponent comment are corrected (jsonb turns `1e2` into 100, which is accepted as that integer). Decisions row q5 added for the NUL refusal.
- **Tester nits.** Rename truncation is grapheme safe (`Intl.Segmenter`); the two red hostile-text cases pass, and U+061C is in the shared set.
- Tests: pgTAP `pack_import.test.sql` now 72 assertions.
