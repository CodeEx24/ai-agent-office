# AGO-107 - US-015 Apply row-level security on every table

## Overview
Epic EP-01 (Data and auth), wave 1, workstream WS-E (Security and Governance), risk tier **high** (tenancy, authorization, data model, human-in-the-loop surface). Jira: https://stratyge.atlassian.net/browse/AGO-107. Blocked by AGO-74 (core schema) and AGO-82 (roles and `private.is_member`), both done. Builds on AGO-102 (run_events append-only) and AGO-122 (seed data).

Acceptance criteria (verbatim):
- Given user A and user B in different workspaces, when A queries any table, then no B rows return
- A test suite covers select, insert, update and delete for every table
- Tables without a policy fail the test run
- Tests pass, no regressions, PR reviewed and merged, docs updated (see Definition of Done)

## Implementation details
One migration, `supabase/migrations/20261106120001_ago_107_rls_every_table.sql`, with its rollback in `supabase/rollbacks/`. It gives `authenticated` exactly the privileges and policies each table needs and nothing else. `anon` holds nothing anywhere. `service_role` (the runtime) is untouched.

**Two gates per command.** Privileges first (column-level where it matters), then a policy built on `private.is_member(workspace_id, min_role)` from AGO-82. Every policy is `to authenticated`, one policy per command, named `<table>_<command>_<minimum role>`. UPDATE policies carry `USING` and `WITH CHECK`.

**Role matrix** (viewer is read-only, member does normal work, owner does governance):

| Table | select | insert | update | delete | Notes |
|---|---|---|---|---|---|
| workspaces | viewer | - | owner | - | AGO-82. `name` column only; created by the onboarding RPC |
| members | viewer | - | - | - | AGO-82. Nobody changes a role through the API, including their own |
| agents | viewer | member | member | owner | `mode` and `status` are not writable: agents always start strict and nobody can loosen them through the API |
| skills | viewer | member | member | member | `version` is not writable (skill library, AGO-128) |
| agent_skills | viewer | member | - | member | re-link instead of update |
| agent_capabilities | viewer | owner | - | owner | `granted_by` must be the caller's own membership; change = delete and re-grant |
| tasks | viewer | member | member | member | `created_by` is null or the caller's own membership |
| runs | viewer | member | - | - | insert queues a run (status defaults to `queued`); the runtime owns the rest; history is never deleted |
| run_events | viewer | - | - | - | append-only and written by the runtime only (AGO-102 untouched) |
| approvals | viewer | - | member | - | humans decide, never create; see below |
| claims | viewer | - | - | - | runtime only |
| budgets_usage | viewer | owner | owner | - | budget columns only; usage counters are runtime-only |
| notes_index | viewer | member | member | member | |

"-" = no privilege and no policy for `authenticated`: only `service_role` or a future human-only RPC can do it.

**Approvals (human in the loop).** `authenticated` can only `UPDATE (status, decided_by, decided_at)`. The policy lets a member decide a row only while it is `pending`, unexpired and unconsumed, only to `approved` or `denied`, and only as themselves (`decided_by = private.current_member_id(workspace_id)`). `payload_hash`, `action`, `agent_id`, `run_id`, `expires_at` and `consumed_at` are not in any grant, so an approval stays bound to the payload hash it was created with and cannot be extended or re-used. An expired approval can no longer be approved (timeout means deny). Agents are never members and have no user JWT, so they cannot reach any of this.

**Workspace pinning.** `workspace_id` (and every id, FK and audit column) is never in an UPDATE grant, so a row cannot be moved to another workspace. INSERT policies check membership on the new `workspace_id`, so a row cannot be planted in a workspace the caller does not belong to. Composite FKs from AGO-74 stop a child pointing at another workspace's parent.

**New helper** `private.current_member_id(workspace_id)`: `security definer`, `stable`, `search_path = ''`, executable by `authenticated` only, answers only about `auth.uid()`. It pins `granted_by`, `decided_by` and `created_by` to the caller. The AGO-82 policies were renamed to the same naming scheme.

**Tests** (`pnpm exec supabase test db`, inside the db lock): 324 assertions across 10 files.
- `rls_catalog.test.sql` (20, AC3): enumerates every table in the API-exposed schemas (`public`, `graphql_public`) and reports any that has RLS off, no policy, a privilege for `authenticated` without a policy for that command, an `anon` privilege, a policy that is not `to authenticated`, is `FOR ALL`, does not call `is_member`, or an UPDATE policy without `WITH CHECK`, a table without a `workspace_id`-led index, a SECURITY DEFINER function without a pinned `search_path`, or a function `anon` can execute. Nine probe tables prove each rule bites, so the check fails closed.
- `rls_every_table.test.sql` (39, AC1 and AC2): fixtures for two workspaces with a row in all 13 tables; 52 cases (13 tables x select, insert, update, delete) run as owner, member, viewer, removed member and an outsider (owner of workspace B), 260 attempts, each compared with the documented matrix; a dynamic per-table visibility check (own rows visible, zero foreign rows) for A and B; targeted cases (cross-workspace insert and move, forged `created_by` / `granted_by` / `decided_by`, hash/expiry/consumption edits, expired approval, agent mode, role self-promotion, run event forgery, usage counters) and the `service_role` runtime paths.
- Eight existing assertions that hard-coded "authenticated has no privileges yet" were updated to the new contract: 1 in `core_schema`, 3 in `core_schema_qa` (now 5 stricter ones), 1 allow-list in `run_events_append_only_qa` (adds `current_member_id`), 3 in `seed_data_qa` (other workspaces now see zero rows instead of a privilege error).
- Real-API check (PostgREST, two users, local stack): B reads 0 of A's tasks and updates/deletes 0 rows; planting a row in A, moving a row to B, setting an agent `mode` and forging a run event all return 403 / `42501`; anon gets 401. Live Playwright specs for AGO-82 (`workspaces-*-live`, 24 tests) still pass.
- Script suites with `RUN_DB_TESTS=1` (seed, run_events): 99 pass when run serially (`--no-file-parallelism`). In parallel `db-seed-qa` can see runs inserted by the run_events suites in the same database (shared-DB race, not caused by this ticket).
- Independent subagent review was not run: the dispatch brief forbids subagents. The self-review below stands in; `/pr-gate` is the independent gate.

### Decisions taken (no human at the keyboard; recommended option chosen each time)
| Decision | Chosen | Why |
|---|---|---|
| Who may write what | Role matrix above | Viewer read-only, member normal work, owner governance (capabilities, budgets, agent deletion, workspace settings) matches the coordinator's rule and the human-in-the-loop invariants. |
| run_events for authenticated | Select only, no insert | AGO-102 left "maybe insert" open. A human inserting events would forge the audit trail; the runtime writes them as `service_role`. |
| Who may decide approvals | Member or owner, as themselves, pending and unexpired only | Normal operations should not bottleneck on owners; the approval row has no tier, so owner-only for Tier 3+ is a follow-up once the policy engine stores it. |
| Immutability mechanism | Column-level UPDATE/INSERT grants plus `WITH CHECK` | A column privilege is stricter than a policy comparison (policies cannot see OLD values) and is simple to test. |
| Agent mode | Not writable through the API | Packs and the UI must land agents in Strict; loosening is a policy decision for a future human-only path. |
| Attribution columns | Pinned with `private.current_member_id` | Without it a member could record someone else as grantor or approver. |
| `private.is_member` per-row cost | Kept as is | The coordinator asked to reuse it. Every table has an index led by `workspace_id` (asserted), so each check is an index lookup. Revisit with `EXPLAIN` at volume (follow-up). |
| Default privileges | Not changed | A future table still starts with Supabase's default grants, but the catalog test fails the run until it has a policy per granted command and nothing for `anon`. Changing default ACLs is a broader change. |
| Migration name | `ago_107` | The brief's constraint 1 mentions `ago_82`, which contradicts CLAUDE.md section 5 and the coordinator notes (`<ts>_ago_107_<what>.sql`); the ticket key wins. |

## API changes
No HTTP route. Data API surface: `authenticated` can now read all 13 tables (membership RLS) and perform the writes in the matrix; PostgREST requests for anything else return 403 / empty. No new RPC. `private.current_member_id` is not callable through the API (the `private` schema is not exposed).

## Database changes
One migration plus rollback. No table or column changes, so `pnpm db:types` produced no diff.
Rollback: apply `supabase/rollbacks/20261106120001_ago_107_rls_every_table.down.sql` (drops the 31 policies, restores the AGO-82 policy names, revokes the grants, drops `private.current_member_id`), then delete the `20261106120001` row from `supabase_migrations.schema_migrations`, or `pnpm db:reset` on the previous commit.
Rollback proof (inside the db lock): before 34 policies and the helper; after the down file 3 policies, no helper, no `authenticated` privilege on `tasks`; `pnpm db:reset` re-applies to 34 policies, `supabase db diff` reports "No schema changes found", `supabase db lint` reports no schema errors, all pgTAP pass.

## Known limitations
- Owner-only approval of Tier 3 and 4 actions is not enforced here: `approvals` has no tier column yet. Tier gating belongs to the policy engine.
- No requester identity on approvals, so "a human cannot approve their own request" is only enforced as far as the data allows (decider = caller, pending, unexpired). Revisit when runs record who queued them.
- `runs` has no update/cancel path for humans; cancelling a run is a later ticket.
- Agent mode / status changes need a future owner-only RPC.
- `private.is_member` is `security definer`, so Postgres cannot inline it; unfiltered scans evaluate it per row. Fine for id- or workspace-filtered queries.
- A new table still receives Supabase's default grants until its migration revokes them; the catalog test is what stops it merging without policies.
- Live E2E needs the local stack, so it does not run in CI.
