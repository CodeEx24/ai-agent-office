# AGO-166 - Add loop detection and run guard rails

## Overview
US-033, epic EP-02, wave 2. Jira: https://stratyge.atlassian.net/browse/AGO-166. Builds on AGO-167 (the agent tool loop with
step, token and wall-time limits). Two acceptance criteria are in scope:

- AC1: the same tool call repeated 3 times with identical output stops the run with a loop event.
- AC2: step, token and time limits are configurable per agent.

## Implementation details
- **Loop detection** (`apps/worker/src/agent/agent-loop.ts`). Every tool result gets a fingerprint:
  `sha256(tool name, canonical JSON of the input, outcome)`, where the outcome is a hash of the full scrubbed output (or the
  error text for a denied or failed call). The loop counts consecutive identical fingerprints across the whole run (steps and
  calls within a step both count). At `LOOP_REPEAT_THRESHOLD` (3) it emits `step.completed` then `run.loop_detected`
  (`tool_name`, `call_hash` = the fingerprint, `repeat_count`) and returns `end: "loop_detected"`. The event never carries
  arguments or output. Canonical JSON already sorts keys, so `{a,b}` and `{b,a}` are the same call.
- **Run end** (`queue/run-processor.ts`). `RunEnd` gains `loop_detected`: the run is marked `failed`, with no `run.completed`;
  `run.loop_detected` is the terminal event (same treatment as `run.limit_reached`).
- **Per-agent limits.** `packages/shared/src/agents/run-limits.ts` holds the bounds (`RUN_LIMIT_BOUNDS`: steps 1-200, tokens
  1,000-5,000,000, wall time 1-840 s), the `LOOP_REPEAT_THRESHOLD` constant, `agentRunLimitsSchema` (Zod, for the future
  settings form and storage) and `clampRunLimit`. `apps/worker/src/agent/run-limits.ts` adds the `RunLimitsResolver`
  interface, `AgentRunLimitsSource` (where an agent's stored overrides come from) and `createRunLimitsResolver`. The loop
  resolves limits once at the start of each run; the agent's steps, tokens and wall time replace the worker-wide ones.
  Overrides are untrusted: a value outside the bounds is clamped (so nobody can set "unlimited"), a non-integer keeps the default,
  and a source that throws falls back to the defaults. `config.ts` now takes its env bounds from the same constants.
- Each limit still emits `run.limit_reached` (steps, tokens, time), unchanged.

## API changes
None (worker internals). New exports from `@ago/shared`: `RUN_LIMIT_BOUNDS`, `RUN_LIMIT_NAMES`, `LOOP_REPEAT_THRESHOLD`,
`agentRunLimitsSchema`, `clampRunLimit`.

## Database changes
None in this PR. The `agents` table has no column for run limits (AGO-74/AGO-141 added role, model, prompt and
`daily_budget_cents` only). The schema slot is held by AGO-148, so storage is a follow-up: add a nullable `run_limits jsonb`
(validated by `agentRunLimitsSchema`, with a check or trigger) to `agents`, expose it in the wizard/settings, and implement
`AgentRunLimitsSource` against it, then pass it in `wire.ts`. Until then every agent runs on the workspace defaults
(`AGENT_MAX_STEPS`, `AGENT_MAX_TOKENS`, `AGENT_MAX_WALL_MS`).

## Decisions taken
| Decision | Choice | Why |
|---|---|---|
| What counts as "the same call" | Same tool name + canonical arguments + same output, consecutive across the run | Matches AC1 exactly; key order cannot hide a repeat. |
| Failed or denied repeats | Counted as a loop, using the error text as the outcome | A call that fails identically every time is as stuck as one that succeeds identically. |
| Fingerprint of output | Hash of the full scrubbed output, not the truncated copy | Two outputs that differ only after the truncation point are still different. |
| Event contents | Tool name, fingerprint hash, count only | No secrets or arguments in the append-only log. |
| Run status on a loop | `failed`, no `run.completed` | Same as limits: a run with no result must not read as succeeded. |
| Per-agent limits without a schema slot | Resolver behind an interface, defaults from config, Zod bounds, no storage yet | The brief says the schema slot is not available; only storage is pending. |
| Out-of-range override | Clamp to the bound (do not reject) | A bad stored value must never block or unbound a run. |
| Near-loops (A,B,A,B) | Not detected; documented follow-up | Not required; needs a window-based detector. |
| Existing AGO-167 QA tests | Two scripted repeats given distinct inputs | They relied on identical calls repeating, which is now (correctly) a loop. |

## Known limitations
- Per-agent limits cannot be stored yet (see Database changes); only the resolver, bounds and loop wiring ship here.
- Only exact consecutive repeats are detected. Alternating patterns (A,B,A,B) and "same call, slightly different output" are not.
- The threshold (3) is a constant, not per agent.

## Testing notes
- `pnpm --filter @ago/worker exec vitest run src/agent/agent-loop.test.ts src/agent/run-limits.test.ts src/queue/run-processor.test.ts`
- Covered: 3 identical calls and outputs -> `run.loop_detected` and stop; same call with different output -> no stop; key-order
  independence; non-consecutive repeats; repeated denial; event has no arguments or output; per-agent steps, tokens and time
  override and emit `run.limit_reached`; override capped at the bound; lookup failure falls back to defaults;
  `loop_detected` ends the run as failed. All use the scripted fake provider: no model API calls.
- No DB test is needed (no schema change); the full suite was run under `node scripts/db-lock.mjs acquire AGO-166`.
